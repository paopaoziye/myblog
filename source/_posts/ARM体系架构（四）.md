# 处理器架构
## ARM体系架构
### ARM体系架构（四）
#### 1.异常与中断
**①简介**
>**概述**：异常是指处理器因**内部或外部事件**暂时改变正常执行流，进入**异常处理程序**，处理完成后再**恢复原执行流**
{%list%}
异常可分为同步异常和异步异常，前者由当前指令直接触发，后者由外部事件触发，与当前指令无直接因果关系
{%endlist%}
>**同步异常**通常在**当前线程/进程上下文**中处理，`IRQ`等**异步硬件异常**通常在**中断上下文**中处理
{%right%}
异常处理程序本质上也是一段可执行代码，但异常进入、现场保存、和异常返回均受到处理器架构规则控制，与普通函数调用不同
{%endright%}
>异常处理程序内部仍然可以**调用普通函数**，但函数调用仍应遵循`AAPCS`等调用约定，正确维护**寄存器与栈结构**
{%warning%}
异常处理期间仍可能被更高优先级异常抢占，因此访问共享数据时需要考虑临界区、原子操作以及代码可重入性等并发问题
{%endwarning%}
{%wrong%}
硬中断上下文通常不能执行会导致当前执行流睡眠、阻塞或等待任务调度的操作，因为中断处理并不具备普通线程的阻塞调度语义
{%endwrong%}

**②异常入口**
>**概述**：异常入口是指异常**满足响应条件后**，处理器依据**异常向量表**和**架构规则**，转入**异常处理程序**的起始过程
{%list%}
程序通常在编译和链接阶段建立异常向量表，按架构规定顺序将各个异常对应的入口地址或入口代码组织到相应表项中
{%endlist%}
>**异常向量表**的位置由**具体架构和处理器实现**决定，可能采用**架构规定的固定位置**，也可采用**可编程基址寄存器**
{%right%}
不同Profile和执行状态下的异常向量表组织方式不同，有的表项直接保存异常处理程序地址，有的表项则存放跳转入口指令
{%endright%}
{%warning%}
进入异常处理程序前需要正确保存打断程序的执行上下文，其中部分状态由硬件自动保存，其余内容由软件按需保存
{%endwarning%}
>执行上下文即能**描述处理器当前程序运行状态**所需的信息，通常涉及**通用寄存器**、`PC`、`SP`和**处理器状态**等

**③异常返回**
>**概述**：异常返回是指**异常处理完成后**，处理器按照架构规则**恢复异常发生前的执行上下文**，并重新回到**原程序执行流**的过程
{%list%}
异常返回通常需要恢复被保存的寄存器、程序计数器和处理器状态等运行现场，具体恢复内容和方式由处理器架构及异常类型决定
{%endlist%}
{%right%}
异常返回后可能重新执行被异常打断的指令，也可能从其后的指令继续执行，具体取决于异常产生原因和体系结构规定
{%endright%}
{%warning%}
中断处理程序在返回前应按照外设规则清除或确认中断请求，否则中断源仍然有效时，处理器返回后可能再次进入同一中断
{%endwarning%}
#### 2.M-profile异常响应
**①NVIC**
>**概述**：也称为**嵌套向量中断控制器**，用于管理`M-profile`处理器中的**中断使能**、**挂起状态**、**优先级**以及**中断嵌套**等功能
{%list%}
NVIC主要维护中断的Enabled、Pending和Active状态，分别用于描述该中断是否允许响应、是否等待处理和是否正在处理
{%endlist%}
>中断产生后通常被置为`Pending`，当中断**使能且满足响应条件时**，处理器才会进入对应的**中断处理程序**，并将其置为`Active`
{%right%}
NVIC支持通过优先级分组将可配置中断的优先级分为抢占优先级和子优先级，其中优先级数值越小，表示逻辑优先级越高
{%endright%}
>当多个中断同时处于`Pending`状态时，**抢占优先级更高**的先执行，**抢占优先级相同时**再由**子优先级**决定先后

>`NVIC`支持**中断嵌套**，即**高抢占优先级中断**可以打断**低抢占优先级中断**从而被`CPU`响应，前者执行完毕之后再继续执行后者

>如果两个中断的**抢占优先级和子优先级均相同**，则由**异常编号**决定响应顺序，通常**异常编号较小**的优先级更高
{%warning%}
Disable一个中断并不代表这个中断不会产生，也不会自动清除它已经存在的Pending状态，更不会打断其处理流程
{%endwarning%}

**②运行模式**
>**概述**：`M-profile`处理器主要有`Thread mode`和`Handler mode`两种运行模式，分别用于执行**普通程序**和**异常处理程序**
{%list%}
M-profile处理器复位后通常进入特权级Thread mode并使用MSP，当异常被响应时则切换到Handler mode
{%endlist%}
>`Thread mode`可以通过`CONTROL.nPRIV`选择在**特权级**还是**非特权级别**运行，`Handler mode`始终运行在**特权级**

>`Thread mode`可以通过`CONTROL.SPSEL`选择使用`MSP`还是`PSP`，而`Handler mode`始终使用`MSP`
{%right%}
支持TrustZone扩展的Armv8-M处理器还可划分为Secure和Non-secure两个安全域，对代码、数据和外设资源进行隔离
{%endright%}
>**安全域**与**运行模式**属于不同维度，因此可以组合形成`Secure Thread mode`、`Non-secure Thread mode`等运行状态
{%warning%}
特权级代码可以通过修改CONTROL.nPRIV进入非特权级，非特权级代码只能通过异常进入特权Handler mode后完成权限切换
{%endwarning%}

**③异常响应流程**
>**概述**：中断被响应后，`CPU`会**自动保存必要的执行上下文**，并跳转到对应的**中断处理程序**，异常返回时再**自动恢复对应上下文**
{%list%}
CPU开始响应异常时，会将一系列寄存器自动压入异常发生前正在使用的栈中，形成一个基本异常栈帧
{%endlist%}
>**基本异常栈帧**包含`R0-R3`、`R12`、`LR`、`PC`和`xPSR`，也就是在`caller-saved`规定的基础上新增了`PC`和`xPSR`

>完成压栈后，`CPU`从**异常向量表**取得**异常处理程序地址**并写入`PC`，同时将`LR`设置为特殊的**异常返回值**`EXC_RETURN`
{%right%}
EXC_RETURN通常表现为0xFFFFFFFx形式，用于告诉处理器异常返回时应恢复到哪种运行模式和使用哪个栈指针
{%endright%}
>`0xFFFFFFFD`是常见的`EXC_RETURN`值，表示异常返回时从`PSP`弹出**异常栈帧**，并切换到`Thread Mode`使用`PSP`
{%warning%}
Thread Mode是否具有特权由CONTROL.nPRIV决定，而进入Handler Mode后处理器始终运行在特权级
{%endwarning%}
```c
/* 任务函数 */
void thread_task(void)
{
    while (1)
    {
        // 1. 假设当前运行状态为：
        //
        //    Mode      = Thread
        //    Privilege = Unprivileged
        //    SP        = PSP
        //
        //    CONTROL.nPRIV = 1   // Thread mode 为非特权级
        //    CONTROL.SPSEL = 1   // Thread mode 使用 PSP
        //
        int x = calculate();

        // 2. 此时 UART 中断发生，NVIC 将对应中断置为 Pending
        //
        // 3. 当 CPU 判断该中断满足响应条件后，开始异常进入：
        //
        //    - 将 R0-R3、R12、LR、PC、xPSR
        //      自动保存到异常发生前正在使用的 PSP
        //
        //    - R4-R11 不属于硬件自动异常栈帧，
        //      需要时由软件/编译器负责保存
        //
        //    - 从 Thread mode 切换到 Handler mode
        //
        //    - Handler mode 开始使用 MSP
        //
        //    - Handler mode 始终是 Privileged，
        //      因此 CPU 此时获得特权执行权限
        //
        //    - CONTROL.nPRIV 仍保持为 1，并没有被清零
        //      只是 nPRIV 只影响 Thread mode，
        //      在 Handler mode 下不会使处理器变成非特权级
        //
        //    - IPSR 更新为当前 UART 中断对应的 Exception Number
        //
        //    - LR 写入 EXC_RETURN
        //      本例为 0xFFFFFFFD：
        //      返回 Thread mode + 使用 PSP + 基本异常栈帧
        //
        //      注意：
        //      EXC_RETURN 并不记录“返回 Privileged 还是 Unprivileged”
        //      Thread mode 的特权级仍由 CONTROL.nPRIV 决定
        //
        //    - 从向量表取得 UART_IRQHandler 地址并开始执行
    }
}


/* 中断服务程序 */
void UART_IRQHandler(void)
{
    // 4. 执行到这里时：
    //
    //    Mode      = Handler
    //    Privilege = Privileged
    //    SP        = MSP
    //
    //    CONTROL.nPRIV = 1
    //
    //    虽然 nPRIV 仍然为 1，
    //    但 Handler mode 天生就是 Privileged，
    //    因此这里仍具有特权级权限
    //
    //    被中断线程的基本异常栈帧仍保存在 PSP 中
    //
    //    LR 中保存 EXC_RETURN，
    //    本例为 0xFFFFFFFD

    // 5. 处理中断
    uint8_t data = UART->DR;

    // 6. ISR 结束后，编译器生成异常返回代码，
    //    通常最终通过 BX LR 将 EXC_RETURN 装入 PC
    //
    //    CPU 识别出 EXC_RETURN 后：
    //
    //    - 根据 EXC_RETURN 判断返回 Thread mode
    //
    //    - 根据 EXC_RETURN 选择 PSP
    //
    //    - 从 PSP 自动恢复 R0-R3、R12、LR、PC、xPSR
    //
    //    - 从 Handler mode 返回 Thread mode
    //
    //    - CONTROL.nPRIV 仍然保持为 1
    //
    //    - 一旦重新进入 Thread mode，
    //      CONTROL.nPRIV 再次生效
    //
    //    - 因此：
    //          Mode      = Thread
    //          Privilege = Unprivileged
    //          SP        = PSP
    //
    //    - 从被中断的位置继续执行
}
```
**④尾链机制**
>**概述**：异常`A`返回时，如果存在另一个**挂起异常**`B`满足**响应条件**，处理器**不会恢复现场**，而是直接把**控制权**转给新的`B`
{%list%}
尾链过程中处理器会保留原异常栈帧，省略连续异常之间重复的出栈和压栈操作，直到最后一个异常处理完成后再统一恢复现场
{%endlist%}
>**无尾链**：**异常栈帧**压栈 `->` 响应异常`A` `->` 恢复**异常栈帧** `->` **异常栈帧**压栈 `->` 响应异常`B` `->` 恢复**异常栈帧**

>**有尾链**：**异常栈帧**压栈 `->` 响应异常`A` `->` 直接响应异常`B` `->` 恢复**异常栈帧**
{%right%}
尾链机制通过省去连续异常之间重复的出栈和压栈操作，可以有效降低中断响应延迟和异常处理开销
{%endright%}
{%warning%}
尾链发生在异常返回阶段，前提是此时已经存在其他处于Pending状态且满足优先级和响应条件的异常
{%endwarning%}
**⑤迟到异常**
>**概述**：异常`A`**已经进入但尚未执行处理程序**时，如果有另一个**更高优先级**的异常`B`后到达，处理器会改为**优先响应**`B`
{%list%}
由于异常A和异常B打断的是同一个原执行上下文，处理器可以复用已经完成的现场保存操作，无需重新建立新的线程异常栈帧
{%endlist%}
>**无该机制**：**线程异常栈帧**压栈 `->` 响应异常`A` `->` `A`**异常栈帧**压栈 `->` 响应异常`B` `->` 恢复`A`**异常栈帧** `->` 继续响应异常`A` `->` 恢复**线程异常栈帧**

>**有该机制**：**线程异常栈帧**压栈（期间`B`到达） `->` 直接响应异常`B` `->` 响应异常`A` `->` 恢复**线程异常栈帧**
{%right%}
迟到异常可减少高优先级异常抢占带来的额外现场保存开销，处理完后还可通过尾链机制继续响应原异常
{%endright%}
{%warning%}
迟到异常发生在异常入口阶段，且后来到达的异常必须具有比原异常更高的可抢占优先级，才会被优先响应
{%endwarning%}
#### 3.M-profile系统异常
**①简介**
>**概述**：由`ARM`**架构本身定义**的异常，用于处理**处理器自身及系统运行过程中**产生的各类系统级事件如**复位和故障等**
{%list%}
在M-profile中，异常号1-15用于系统异常，不同架构版本和处理器型号实际支持的异常类型可能有所不同
{%endlist%}
>`1.Reset`：用于**系统复位和启动**，通常从复位处理程序开始完成**基础硬件初始化**、`.data/.bss`初始化，并最终进入`main()`执行

>`2.NMI`：用于处理**不可屏蔽的高优先级异常事件**，通常用于**时钟故障**和**电源异常**等需要立即处理的**关键硬件故障**

>`3.HardFault`：用于处理**严重处理器故障**以及其他可配置`Fault`**无法处理**或发生**优先级升级**后的故障

>`4.MemManage`：用于处理**内存保护和访问权限错误**，如违反`MPU`**访问权限**或执行**不可执行区域**中的代码

>`5.BusFault`：用于处理**总线访问故障**，包括**取指**、**数据访问**或**存储器传输过程**中发生的总线错误

>`6.UsageFault`：用于处理**指令执行和处理器使用错误**，如**未定义指令**、**非法执行状态**和**部分非对齐访问**等

>`7.SecureFault`：用于处理`TrustZone`中的**安全属性和安全访问违规**，仅存在于支持`Security Extension`的`Armv8-M`处理器中

>`Exception 8-10、13`：属于**保留异常号**，当前架构**不定义**对应的具体异常用途

>`11.SVCall`：用于通过`SVC`指令**主动请求系统服务**，常用于普通线程进入特权`Handler`执行**操作系统内核功能**

>`12.DebugMonitor`：用于处理**调试相关事件**，使**断点**和**观察点**等调试事件能够通过`DebugMonitor`**异常处理程序**进行调试

>`14.PendSV`：用于执行**可挂起的系统服务异常**，通常设置为**最低优先级**并用于`RTOS`的**任务上下文切换**

>`15.SysTick`：用于处理`SysTick`定时器产生的**周期性系统节拍**，常用于**系统计时**、**任务延时**和**触发任务调度**
{%right%}
SVC、PendSV和SysTick可以构成一个极简RTOS的异常机制基础，分别用于陷入内核、任务切换和任务调度
{%endright%}
{%warning%}
MemManage、BusFault、UsageFault、DebugMonitor和SecureFault等异常并非所有M-profile处理器都完整实现
{%endwarning%}
>`Cortex-M0/M0+`不提供独立的`MemManage`、`BusFault`和`UsageFault`，相关故障通常统一进入`HardFault`

**②Fault体系**
>**概述**：`M-profile`的完整`Fault`体系包括`MemManage`、`BusFault`、`UsageFault`和`HardFault`
{%list%}
MemManage、BusFault和UsageFault都是独立的可配置异常，但是HardFault始终使能且具有固定的高优先级
{%endlist%}
{%right%}
如果MemManage、BusFault、UsageFault对应的故障发生但对应的Fault Handler不允许执行就会升级为HardFault
{%endright%}
>当一个普通`Fault`升级为`HardFault`时，`HFSR.FORCED = 1`会被置位，并通过`CFSR`查询具体**故障类型与原因**

{%warning%}
故障升级原因通常为对应Fault没有使能、对应Fault处理函数中再次产生同类Fault或Fault优先级不够高
{%endwarning%}
>`Fault`优先级不够高主要体现在其余**异常处理函数**触发了对应`Fault`但是其无法抢占触发`Fault`的异常

**③系统控制寄存器**
>**概述**：也称为`SCB`，主要用于管理处理器自身的**异常**、**向量表**、**系统行为**、**低功耗**以及`Fault`状态等系统级功能
{%list%}
部分SCB寄存器属于只读能力描述寄存器，用于向系统软件和调试器提供处理器型号、架构版本以及所支持功能等信息
{%endlist%}
>`CPUID`：用于标识**处理器身份和版本**，记录**实现厂商**、**架构版本**、**处理器型号**、`Variant`和`Revision`等信息

>`ID_PFR`：用于描述处理器支持的**程序员模型**和**处理器功能特性**，如**异常模型**、**执行状态**及**部分架构能力**

>`ID_DFR`：用于描述处理器支持的**调试功能**和**调试架构能力**，供调试器判断可使用哪些**硬件调试机制**

>`ID_AFR`：用于描述处理器实现的**辅助架构特性**，通常用于表示**未归入其他`ID`寄存器的实现相关能力**

>`ID_MMFR`：用于描述处理器支持的**内存模型**和**内存管理能力**，如`MPU`、**内存属性**及**相关内存系统特性**

>`ID_ISAR`：用于描述处理器支持的**指令集架构特性**，如是否实现某些**算术**、**位操作**、**同步**或**其他可选指令**
{%right%}
部分SCB寄存器用于配置处理器的异常处理、运行状态和系统行为，是底层系统软件的重要控制接口
{%endright%}
>`ICSR`：主要管理**系统异常调度状态**，如**当前正在执行的异常**、**最高优先级挂起异常**和`PendSV`**的挂起状态**等

>`VTOR`：主要管理**异常向量表基地址**，使处理器能够根据`Exception Number`找到对应的**异常处理程序**

>`AIRCR`：主要管理**异常优先级分组**和**系统复位**，如**划分抢占优先级与子优先级**和**请求系统复位**等

>`SCR`：主要管理**睡眠和低功耗行为**，如**深度睡眠**、**异常返回后继续睡眠**和**挂起事件唤醒**等

>`CCR`：主要用于配置处理器的**运行行为**和**异常检查规则**，如**除零陷阱**、**非对齐访问检查**和**异常栈对齐**等

>`SHPR`：主要用于设置**系统异常优先级**，如`SVCall`、`PendSV`、`SysTick`及部分可配置`Fault`

>`SHCSR`：主要用于控制并记录**系统异常的使能和运行状态**，如`SVCall`、`PendSV`、`SysTick`及部分`Fault`

>`CPACR`：用于控制**协处理器**或**可选执行单元**的访问权限，典型用途是配置`FPU`相关协处理器的**访问权限**
{%warning%}
部分SCB寄存器专门保存Fault诊断信息，可用于判断故障类型、产生原因以及相关的故障访问地址
{%endwarning%}
>`CFSR`：主要记录**可配置`Fault`的具体故障原因**，包括`MemManage`、`BusFault`和`UsageFault`的状态信息

>`HFSR`：主要记录`HardFault`的**产生原因**，用于判断是否由**其他`Fault`升级**或**其他严重故障**导致

>`DFSR`：用于记录**调试异常的触发原因**，如**断点**、**观察点**、**向量捕获**以及**外部调试请求**等

>`MMFAR`：主要记录发生`MemManage Fault`时的**故障内存地址**，需通过`CFSR.MMARVALID`判断地址是否有效

>`BFAR`：主要记录发生`BusFault`时的**故障访问地址**，需通过`CFSR.BFARVALID`判断地址是否有效

>`AFSR`：用于记录**实现定义的辅助`Fault`信息**，由具体处理器或`SoC`实现提供**额外的故障诊断信息**
