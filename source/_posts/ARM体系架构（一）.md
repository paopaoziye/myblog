# 处理器架构
## Arm体系架构
### Arm体系架构（一）
#### 1.引言
**①简介**
>**概述**：`Arm`是一种以**精简指令集**`RISC`理念为基础的**处理器架构家族**，兼顾了优秀的**执行效率**、**能效表现**和**可扩展性**
{%list%}
Arm体系架构是一套处理器的行为规范，规定指令集、寄存器模型、内存访问机制、异常与中断处理和特权级划分等内容
{%endlist%}
>`Arm`体系架构一般不规定**流水线级数**、**缓存大小**和**主频**等具体**硬件实现细节**，通常由**芯片设计厂商**自行实现
{%right%}
Arm主要提供A、R和M三类架构Profile，分别面向应用处理器、实时处理器和微控制器等不同应用场景
{%endright%}
>每类`Profile`又包含`Armv7`、`Armv8`、`Armv9`等不同**架构版本**，更早还有`Armv1-Armv6`等架构，但是没有分类体系

>不同`Arm`架构版本会在**指令集**、**位宽**、**内存管理**、**安全机制**和**扩展功能**等方面不断演进，例如`Armv8-A`引入了`AArch64`执行状态
{%warning%}
Cortex-A、Cortex-R和Cortex-M是Arm公司基于相应架构Profile设计的处理器核系列，可以理解为Arm架构规范的具体实现
{%endwarning%}
>比如`Cortex-M33`基于`Armv8-M`架构，`Cortex-A53`和`Cortex-A72`基于`Armv8-A`架构，而`Cortex-R52`则基于`Armv8-R`架构

>**芯片厂商**可以在这些**处理器核**上集成**存储器**、**总线**、**外设**及其他**功能模块**，设计成完整的`MCU`、`SoC`或其他类型的**处理器芯片**

**②执行状态**
>**概述**：`Arm`定义了`AArch32`和`AArch64`两种执行状态，支持哪种状态取决于**架构`Profile`**、**架构版本**和**处理器具体实现**
{%list%}
AArch32与AArch64的主要区别体现在寄存器位宽与数量、所使用的指令集、地址空间以及异常与特权模型等方面
{%endlist%}
>`AArch32`可使用`A32`或`T32`指令集，而`AArch64`使用重新设计的`A64`指令集

>`AArch32`提供`R0~R15`等**32位通用寄存器**，而`AArch64`提供`X0~X30`共 **31个64位通用寄存器**，寄存器资源更加丰富

>`AArch32`采用传统的`User`、`SVC`、`IRQ`、`FIQ`等处理器模式，而`AArch64`采用`EL0~EL3`**异常级模型**管理不同的特权级

>`AArch32`主要采用**32位地址模型**，而`AArch64`支持更大的**虚拟地址空间和物理地址空间**，更适合现代操作系统
{%right%}
在同时支持AArch32和AArch64的处理器中，通常可以在异常进入或异常返回过程中结合目标异常级的配置完成两种状态的转换
{%endright%}
{%warning%}
M-Profile不采用AArch32/AArch64的执行状态划分，而是采用面向微控制器的32位程序员模型，并仅执行T32指令集
{%endwarning%}
{%wrong%}
两种执行状态在系统寄存器、异常机制和SIMD模型等方面也存在差异，因此AArch64并非只是AArch32的简单64位扩展
{%endwrong%}
**③指令集**
>**概述**：`Arm`体系架构主要包括`A32`、`T32`和`A64`三种指令集，用于规定处理器**可执行的指令**及其**编码格式**和**基本行为**
{%list%}
A32和A64都采用固定32位指令编码，而T32由Thumb指令集发展而来，引入Thumb-2形成了混合使用16位和32位编码的指令体系
{%endlist%}
>`Thumb`指令集以`16`位编码为主，目的是**提高代码密度**，`Thumb-2`在其基础上加入大量`32`位编码指令**完善其功能**

>此外，`A32`、`T32`和`A64`在**寄存器使用**、**寻址方式**、**条件执行方式**、**分支控制**和**扩展支持**等方面均存在差异
{%right%}
A32指令规整且兼容性好，T32在兼顾功能的同时具有较高的代码密度，而A64寄存器资源丰富、地址空间大且64位运算能力强
{%endright%}
{%warning%}
A32和T32可以在同一个AArch32程序中协同使用，但需要通过特定的分支指令在两种指令集状态之间切换
{%endwarning%}
{%wrong%}
A64不能与A32或T32指令直接混合执行，从AArch32代码迁移到AArch64时，通常需要针对A64重新编译或适配
{%endwrong%}

#### 2.寄存器模型
**①AArch32寄存器模型**
>**概述**：在`AArch32`执行状态下，程序通常可见`16`个`32`位寄存器`R0-R15`，以及**当前程序状态寄存器**`CPSR`，如下所示
{%list%}
R0-R12为通用寄存器，R13、R14和R15则分别具有SP、LR和PC的专用含义，分别表示栈指针寄存器、链接寄存器和程序计数器
{%endlist%}
>`R0-R12`主要用于**数据运算**、**参数传递**、**临时数据保存**和**地址计算**等，其具体用途还需要遵循`AAPCS32`**调用约定**

>`SP`指向**当前栈顶**，栈通常用于保存**函数局部变量**、**函数调用现场**、**中断现场**和**任务上下文**等临时数据

>`LR`通常保存**函数调用**或**异常处理**所需的**返回信息**，前者可通过`BX LR`等方式返回，后者则需要相应的**异常返回机制**恢复执行

>`PC`用于保存和控制处理器的**指令执行位置**，**分支跳转**、**函数调用**、**函数返回**和**部分加载指令**可以更新`PC`以改变**程序执行流**

>`CPSR`用于保存处理器的**当前运行状态**，包括**条件标志位**、**当前执行状态**、**中断屏蔽状态**和**处理器模式**等信息
{%right%}
部分异常模式拥有银行化寄存器，异常进入和返回过程中能够更快地保存、切换和恢复关键现场，减少软件手动保存寄存器的开销
{%endright%}
>**银行化寄存器**是指处理器切换到**对应异常模式**后，相同的寄存器编号会**自动映射到另一组独立的物理寄存器**

>`SPSR`用于保存**异常发生前**的`CPSR`，因为**异常发生时**处理器需要改变`CPSR`，故将其保存到`SPSR`，直到**异常返回**再恢复
{%warning%}
如果函数内部还需要调用其它函数，新的调用会更新LR中的返回地址，因此通常需要提前将原有LR保存到栈中，并在返回前恢复
{%endwarning%}
**②AArch64寄存器模型**
>**概述**：`AArch64`定义了`31`个`64`位**通用寄存器**`X0-X30`，同时提供**栈指针**`SP`、**零寄存器**`XZR`以及**描述当前处理器状态**的`PSTATE`
{%list%}
每个X0-X30都可以通过对应的W0-W30访问其低32位，向Wn写入数据时，对应Xn的高32位会自动清零
{%endlist%}
>`X29`通常作为**帧指针**`FP`，用于建立和定位**当前函数的栈帧结构**，`X30`为链接寄存器`LR`，用于保存**函数调用的返回地址**

>`SP`是**独立的栈指针寄存器**，不属于`X0-X30`通用寄存器组，只能在支持`SP`操作数的**部分数据处理和访存指令**中使用

>`XZR`是特殊的**零寄存器**，读取时始终得到`0`，写入的数据则**直接丢弃**，可以避免为了读取常量`0`而**额外分配一个真实寄存器**

>`AArch64`不再使用类似`AArch32 CPSR`的**单一程序状态寄存器**，而是使用一组**程序状态字段**，统称为`PSTATE`
{%right%}
AArch64中的程序计数器由处理器内部维护，主要通过分支、异常和PC相对寻址等机制使用，使指令编码和流水线行为更加规整
{%endright%}
>`AArch64`的不同异常级别提供对应的`SPSR_ELx`保存**异常发生前的程序状态**，并使用`ELR_ELx`保存**异常返回地址**

>`AArch64`还提供`32`个`128`位`SIMD&FP`寄存器`V0-V31`，可按**不同宽度访问**，可用于**浮点运算**、**向量运算**、**加密和媒体处理**等
{%warning%}
X29作为帧指针主要由AAPCS64和具体平台的调用约定决定，若允许省略帧指针，它也可以作为普通的被调用者保存寄存器使用
{%endwarning%}
{%wrong%}
A64指令编码中的寄存器编码值31具有特殊含义，根据具体指令可能表示栈指针寄存器SP或零寄存器XZR
{%endwrong%}
**③M-profile寄存器模型**
>**概述**：`M-Profile`的寄存器模型类似于`AArch32`，但是针对`MCU`和**实时控制场景**简化了**处理器状态**、**异常处理**和**栈管理机制**
{%list%}
M-Profile保留R0-R15，并将程序状态拆分到xPSR中，并采用PRIMASK、BASEPRI、FAULTMASK和CONTROL完成中断和权限管理
{%endlist%}
>`xPSR`是程序状态寄存器的组合视图，可分为`APSR`、`IPSR`和`EPSR`字段，分别用于记录**运算状态**、**当前异常编号**和**指令执行状态**

>`CONTROL`主要控制`Thread mode`的**特权级**和**栈指针选择**，在支持**浮点扩展**的处理器中，还可包含**浮点上下文**状态相关控制信息

>`PRIMASK`用于屏蔽所有**可配置优先级**的异常，提供一种简单的**全局异常屏蔽机制**，但不包括`NMI`和`HardFault`

>`BASEPRI`用于设置一个**优先级阈值**，优先级数值**大于或等于该阈值的可配置异常**将被屏蔽，同样不能屏蔽`NMI`和`HardFault`

>`FAULTMASK`用于进行**最高级别的异常屏蔽**，置位后可屏蔽除`NMI`外的所有异常，包括`HardFault`
{%right%}
M-Profile提供MSP和PSP两套栈指针，其中MSP常用于系统启动和异常处理，而PSP常用于应用线程或RTOS任务
{%endright%}
>在`Thread mode`下可以通过`CONTROL.SPSEL`选择使用`MSP`或`PSP`，进入`Handler mode`后则始终使用`MSP`
{%warning%}
M-Profile的异常处理不依赖传统的银行化通用寄存器，进入异常时由硬件自动保存部分关键现场，并在异常返回时恢复
{%endwarning%}
{%wrong%}
不同M-Profile架构版本和Cortex-M内核支持的特殊寄存器并不完全相同，比如Cortex-M0不提供BASEPRI和FAULTMASK
{%endwrong%}
#### 3.过程调用标准
**①简介**
>**概述**：也称为`PCS`，是`ABI`的重要组成部分，用于规定**调用者与被调用者**之间的**函数调用接口**和**行为约定**
{%list%}
过程调用标准主要规定参数与返回值传递、寄存器保存责任、栈的使用与对齐以及函数调用过程等基本规则
{%endlist%}
>`Arm`主要提供面向`AArch32`的`AAPCS32`和面向`AArch64`的`AAPCS64`，用于规范**不同执行环境下**的过程调用方式

>`ABI`从更高层规定二进制程序之间的兼容接口，使不同编译器生成的**目标文件**、**库文件**和**程序模块**能够**正确链接并协同运行**

>除过程调用标准外，`ABI`通常还涉及**数据类型布局**、**目标文件格式**、**符号与链接规则**以及**异常展开**等内容
{%right%}
高级语言编译器通常会根据目标架构、操作系统和编译选项，自动按照相应的PCS和ABI生成函数调用代码
{%endright%}
{%warning%}
汇编代码与编译器生成的代码交互时，同样需要遵循相应的PCS，并确保各程序模块采用兼容的ABI约定
{%endwarning%}
{%wrong%}
AAPCS并不定义处理器的硬件异常进入和返回机制，但异常处理程序调用普通函数时，仍需要遵循相应的AAPCS
{%endwrong%}
**②AAPCS32**
>**概述**：规定`AArch32`的函数调用规则，采用**满递减栈模型**，即栈空间向**低地址方向**增长，`SP`始终指向**当前栈顶位置**
{%list%}
函数参数优先通过R0-R3传递，寄存器不足时则使用栈传递，对于需要两个连续寄存器的64位参数，采用R0-R1或R2-R3传递
{%endlist%}
>对于**返回值**，不超过`32`位的数据通常通过`R0`返回，`64`位数据通常通过`R0-R1`返回，`128`位的**容器化向量**通常通过`R0-R3`返回

>如果返回值为较大的**结构体或复合数据类型**，通常由**调用者预先提供存储空间**，并通过**隐式参数**传递地址，由**被调用函数**写入
{%right%}
AAPCS32规定调用者负责保存可能被覆盖的R0-R3、R12和LR，被调用者负责恢复需要保持不变的R4-R11和SP
{%endright%}
>**调用者**需要保存`LR`是因为**函数调用指令**`BL`和`BLX`会将返回地址写入`LR`，从而**覆盖原有内容**

>**被调用者**保存`R9`的规则取决于**具体平台**`ABI`，当`R9`被定义为**普通被调用者保存寄存器**时，需要保证其值不变
{%warning%}
R9在部分平台中具有特殊用途，例如保存静态基址或线程局部存储指针，除非明确目标平台约定，否则不应随意修改
{%endwarning%}
>**静态基址**用于保存访问**静态数据区域**的基准地址，程序可以通过它快速定位**全局变量**或**静态变量**

>**线程局部存储指针**用于指向**当前线程**独有的数据区域，使程序能够快速访问**线程私有变量**
{%wrong%}
AAPCS32要求SP至少保持4字节对齐，并在公共函数调用边界即被调用函数开始执行时保持8字节对齐
{%endwrong%}
```nasm
.syntax unified
.cpu cortex-m3
.thumb

.global _start
.type _start, %function
.thumb_func

; 调用者
_start:
    ; 假设 SP 已初始化，并满足 AAPCS32 的 8 字节对齐要求

    ; 准备参数：
    ; 前四个参数通过 R0-R3 传递
    MOVS    R0, #1
    MOVS    R1, #2
    MOVS    R2, #3
    MOVS    R3, #4

    ; 为第五个参数分配栈空间
    ; 同时保证公共函数调用边界满足 8 字节对齐
    SUB     SP, SP, #8

    ; 第五个参数通过栈传递
    MOVS    R12, #5
    STR     R12, [SP, #0]

    ; 调用函数 calculate
    BL      calculate

    ; 清理栈参数区
    ; 返回值保存在 R0 中
    ADD     SP, SP, #8

end_loop:
    B       end_loop

.size _start, .-_start


.global calculate
.type calculate, %function
.thumb_func

; 被调用者
;
; 函数原型：
; int calculate(int a, int b, int c, int d, int e);
;
; 参数：
;   R0       = a
;   R1       = b
;   R2       = c
;   R3       = d
;   [入口SP] = e
;
; 返回值：
;   R0 = result
;
; 计算：
;   result = (a+b)*(c+d)+e

calculate:
    ; 保存被调用者需要保护的寄存器
    ; 同时保存 LR，避免后续调用覆盖返回地址
    PUSH    {R4-R6, LR}

    ; 读取第五个参数 e
    ; PUSH 保存4个寄存器，共占用16字节
    LDR     R4, [SP, #16]

    ; 计算 (a+b)*(c+d)+e
    ADD     R5, R0, R1
    ADD     R6, R2, R3
    MUL     R5, R5, R6
    ADD     R0, R5, R4

    ; 恢复寄存器并返回
    POP     {R4-R6, PC}

.size calculate, .-calculate
```
**③AAPCS64**
>**概述**：规定`AArch64`的函数调用规则，采用**满递减栈模型**，即栈空间向**低地址方向**增长，`SP`始终指向**当前栈顶位置**
{%list%}
整数和指针类型参数优先通过X0-X7传递，浮点和向量类型参数优先通过V0-V7传递，当寄存器空间不足时，剩余参数通过栈传递
{%endlist%}
>对于**返回值**，不超过`64`位的**整数和指针**通常通过`X0`返回，`128`位整数通常通过`X0-X1`返回

>**标量浮点数据或短向量类型**通常通过`V0`返回，而`HFA/HVA`等**复合浮点或向量类型**可通过`V0-V3`返回

>对于无法通过寄存器返回的**大型结果类型**，通常由**调用者提供存储空间**，并通过`X8`传递**该存储空间地址**，由**被调用函数**写入
{%right%}
AAPCS64规定调用者负责保存可能被覆盖 X0-X17和LR，被调用者负责保存需要保持不变的X19-X29和SP
{%endright%}
{%warning%}
类似地，X18部分平台中具有特殊用途，例如保存静态基址或线程局部存储指针，除非明确目标平台约定，否则不应随意修改
{%endwarning%}
{%wrong%}
AAPCS64规定通过SP访问内存时，以及进入公共函数调用边界即被调用函数开始执行时，SP必须保持16字节对齐
{%endwrong%}
```nasm
.arch armv8-a

.text
.balign 4

.global _start
.type _start, %function


; 调用者
_start:

    ; 假设 SP 已初始化，并满足 AAPCS64 的 16 字节对齐要求

    ; 前8个64位整数参数通过 X0-X7 传递
    MOV     X0, #1
    MOV     X1, #2
    MOV     X2, #3
    MOV     X3, #4
    MOV     X4, #5
    MOV     X5, #6
    MOV     X6, #7
    MOV     X7, #8


    ; 第9个参数通过栈传递
    ; 额外分配16字节，保持SP 16字节对齐
    SUB     SP, SP, #16

    MOV     X9, #9
    STR     X9, [SP,#0]


    ; 公共函数调用边界
    ; 此时 SP 满足16字节对齐
    BL      calculate


    ; 清理栈参数区
    ; 返回值保存在 X0
    ADD     SP, SP, #16


end_loop:
    B       end_loop


.size _start, .-_start



.global calculate
.type calculate, %function


; 被调用者
;
; int64_t calculate(
;     int64_t a,b,c,d,e,f,g,h,i
; );
;
; 参数：
;   X0-X7    = a-h
;   [入口SP] = i
;
; 返回：
;   X0 = result
;
; result=(a+b)*(c+d)+e+f+g+h+i


calculate:

    ; 创建64字节栈帧
    ; 保存 FP(X29) 和 LR(X30)
    STP     X29, X30, [SP,#-64]!

    MOV     X29, SP


    ; 保存被调用者保存寄存器
    STP     X19, X20, [SP,#16]
    STP     X21, X22, [SP,#32]


    ; 函数入口SP位于当前FP上方64字节处
    ; 第9个参数位于 [X29,#64]
    LDR     X21, [X29,#64]


    ; 计算(a+b)*(c+d)
    ADD     X19, X0, X1

    ADD     X20, X2, X3

    MUL     X19, X19, X20


    ; 加上e、f、g、h、i
    ADD     X19, X19, X4
    ADD     X19, X19, X5
    ADD     X19, X19, X6
    ADD     X19, X19, X7

    ADD     X0, X19, X21


    ; 恢复被调用者保存寄存器
    LDP     X21, X22, [SP,#32]
    LDP     X19, X20, [SP,#16]


    ; 恢复FP、LR和SP
    LDP     X29, X30, [SP],#64


    ; 返回
    RET


.size calculate, .-calculate
```
