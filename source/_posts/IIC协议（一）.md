# 串行协议
## IIC协议
### IIC协议（一）
#### 协议简介
**①引言**
>**概述**：也称为**集成电路总线**，是一种常用的**同步半双工串行通信方式**，主要用于**短距离**、**中低速**的**多设备通信**，采用`MSB First`
{%list%}
典型IIC由SCL和SDA线组成，前者用于传输时钟信号，后者用于传输数据信号，并且IIC将设备分为主设备和从设备
{%endlist%}
>**主设备**：负责**发起通信**并产生**时钟信号**，通过发送**从机地址**选择需要通信的设备，同时决定本次通信**是读还是写**

>**从设备**：持续**监听总线地址**，在地址匹配后通过`ACK`响应主设备，并按照主设备指定的**读写方向**完成**数据接收或发送**
{%right%}
SCL和SDA通常采用开漏输出结构，设备只能主动拉低总线或释放总线，高电平由外部上拉电阻提供，从而实现逻辑线与
{%endright%}
>**开漏结构**让所有设备**不能主动拉高总线**，因此多个设备可以**安全共享**同一根`SDA`和`SCL`，并实现**总线仲裁**和**时钟拉伸**

>**逻辑线与**：当**所有设备都释放总线**时，总线被**上拉电阻**拉到高电平，当**任意一个设备输出低电平**时，总线变为低电平

>**总线仲裁**：主机发送**逻辑**`1`时发现**总线实际为低电平**，就知道有**其他主机正在拉低总线**，于是判定自己**失去仲裁并停止发送**

>**时钟拉伸**：当从机暂时**无法继续处理数据时**，可以在主机释放`SCL`后继续将其**拉低并保持低电平**，使主机**暂停后续通信**
{%warning%}
IIC总线必须具有合适的上拉电阻，上拉电阻过大会导致信号上升沿过慢，上拉电阻过小则会增加低电平状态下的灌电流和功耗
{%endwarning%}
**②帧格式**
>**概述**：典型的`IIC`通信帧由**起始信号**、**从机地址**、**读写位**、**应答位**、**数据段**和**停止信号**组成，并以设定的**通信速率**传输
{%list%}
一次典型通信可以表示为START -> Address + R/W -> ACK -> Data -> ACK -> ... -> STOP，总线空闲时SCL和SDA均为高电平
{%endlist%}
>**起始信号**：当`SCL`**保持高电平时**，`SDA`由**高电平变为低电平**，通知总线上的**所有从设备**一次新的通信即将开始

>**从机地址**：用于选择当前需要通信的**从设备**，通常是`7 bit`**从机地址**，随后再发送`1 bit`的**读写位**，可以整体视作为**第一个数据段**

>**读写位**：用于指定本次通信的**数据传输方向**，`R/W = 0`表示主设备向从设备**写数据**，`R/W = 1`表示主设备从从设备**读数据**

>**应答位**：每传输完`8 bit`**数据**后，第`9`个时钟用于应答；`ACK = 0`表示**接收方应答**，`NACK = 1`表示**未应答或不再继续接收**

>**数据段**：长度为`8 bit`，通常采用`MSB First`，即**高位先发送**，每传输完一个字节后，接收方都会在第`9`个时钟周期应答

>**停止信号**：当`SCL`**保持高电平时**，`SDA`由**低电平变为高电平**，表示当前**通信结束并释放总线**
{%right%}
主设备在不发送停止信号且不释放总线的情况下，再次产生一个START条件，用于在同一次通信过程中重新寻址或切换读写方向
{%endright%}
{%warning%}
发送方在传输完8 bit后释放SDA，由接收方在第9个时钟周期产生ACK/NACK，发送方通过监听SDA电平判断应答结果
{%endwarning%}
{%wrong%}
传输数据和ACK/NACK应答位时，SDA只能在SCL为低电平时改变状态，并在SCL为高电平时保持稳定以保证接收方能够正确采样
{%endwrong%}
**③发送流程**
>**概述**：`IIC`的发送流程为`CPU -> TXDR -> TX FIFO -> TX Shift Register -> SDA`，其中部分`IIC`外设可能**不提供**`TX FIFO`
{%list%}
发送开始前主设备需要通过控制寄存器CR2配置从机地址、读写方向、传输长度以及START、AUTOEND、RELOAD等传输控制信息
{%endlist%}
>在`IIC`发送过程中，可以通过`BUSY`、`TXIS`、`NACKF`、`TC`、`TCR`和等`STOPF`标志位判断**总线状态**和**发送结果**

>`BUSY`表示总线处于**忙状态**，`TXIS`表示`TXDR`可以写入**新的发送数据**，`NACKF`表示接收到`NACK`，`STOPF`表示检测到**停止信号**

>`TC`表示**当前配置的一段传输**已经完成，等待软件产生**停止信号**结束通信或重新配置`CR2`后产生`Repeated START`开启**新的传输**

>`TCR`表示当前一段传输完成后进入**重载阶段**，此时总线仍**保持通信状态**，需要**重新配置下一段传输**的`NBYTES`等参数
{%right%}
连续发送多个字节时，通常只需要在TXIS置位后不断向TXDR写入数据，无需每发送一个字节都重新配置CR2
{%endright%}
{%warning%}
TC只表示当前配置的一段传输完成，并不一定表示整个IIC通信结束，只有产生STOP并置位STOPF后，才表示本次通信已经结束
{%endwarning%}

**④接收流程**
>**概述**：`IIC`的接收流程为`SDA -> RX Shift Register -> RX FIFO -> RXDR -> CPU`，其中部分`IIC`外设可能**不提供**`RX FIFO`
{%list%}
主设备接收前同样需要配置控制寄存器CR2并完成从机寻址，但需要将传输方向设置为读，随后由从设备向主设备发送数据
{%endlist%}
>接收过程中最主要的状态标志为`RXNE`，表示`RXDR`中已经存在**待读取数据**，`CPU`读取后硬件**继续接收后续数据**
{%right%}
连续接收多个字节时，主设备对前面的字节返回ACK表示继续接收，对最后一个字节返回NACK表示结束接收
{%endright%}
>支持`NBYTES`的`STM32 IIC`外设通常可以**由硬件自动完成该过程**，并在启用`AUTOEND`时自动产生**停止信号**
{%warning%}
主设备接收时，如果RXDR未及时读取，IIC外设通常会暂停SCL等待CPU处理，读取完成后再继续接收后续数据
{%endwarning%}

**⑤错误标志**
>**概述**：`IIC`可以通过`BERR`、`ARLO`、`OVR`和`TIMEOUT`等错误标志判断是否发生**总线错误**、**仲裁丢失**、**数据溢出**和**通信超时**
{%list%}
IIC发生异常时，硬件会置位对应的错误标志，CPU可通过读取状态寄存器判断当前故障类型
{%endlist%}
>`BERR`：表示检测到**总线时序错误**，例如通信过程中出现不符合协议要求的**起始信号**和**停止信号**

>`ARLO`：表示主设备在**多主机仲裁过程中**检测到发送电平与实际总线电平不一致，从而**失去总线控制权**

>`OVR`：表示发生**接收溢出**或**发送欠载**，通常出现在**从机模式且禁止时钟拉伸时**，`CPU`未及时读取`RXDR`或写入`TXDR`

>`TIMEOUT`：表示**总线状态**长时间未发生预期变化，可能由**从设备长时间拉低时钟**、**总线锁死**或**设备异常**引起
{%right%}
多个错误标志可能同时出现，实际排查时应结合当前通信阶段和总线电平状态共同判断异常原因
{%endright%}
{%warning%}
多数错误标志在异常发生后会被硬件锁存，需要软件按照芯片参考手册规定的方式清除，否则可能影响后续通信
{%endwarning%}
**⑥总线锁死**
>**概述**：指`SDA`或`SCL`**被从设备持续拉低**，导致总线**无法恢复到空闲状态**，使主设备无法正常产生**新的起始信号并继续通信**
{%list%}
常见原因是通信过程中主设备异常复位、掉电或传输被中断，而从设备仍停留在原来的通信状态并继续占用总线
{%endlist%}
>**`SDA`锁死**：从设备仍认为**当前传输尚未结束**，因此持续拉低`SDA`，主设备无法重新产生正常的**起始信号**

>**`SCL`锁死**：从设备持续拉低`SCL`，可能是**异常的时钟拉伸**或**设备内部状态异常**引起，使主设备无法继续产生**时钟信号**
{%right%}
当SDA持续被拉低时，主设备可临时将SCL配置为GPIO，主动产生最多约9个时钟脉冲，使从设备继续运行并释放SDA
{%endright%}
>因为一个`IIC`字节通常由`8 bit`数据和`1 bit`应答组成，因此`9`个`SCL`时钟脉冲通常可以**使卡在字节传输中的从设备完成传输**
{%warning%}
总线恢复前应先判断是SDA还是SCL被持续拉低，若SCL本身无法释放，说明从设备仍在持续占用时钟线，通常需要复位从设备
{%endwarning%}
